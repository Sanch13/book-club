# DEPLOY.md — деплой книжного клуба Miran

Рабочая инструкция. Продуктовые решения — в `PROJECT_CONTEXT.md`.

---

## 1. Схема: что где лежит

**Образ неизменяем и содержит код. Состояние живёт в томах.**

| Где | Что |
|---|---|
| образ | код (`src/`), шаблоны, исходники статики (`static/`), зависимости |
| том `db_data` | SQLite |
| том `media_data` | загрузки книг (PDF/MP3/MP4) |
| том `static_data` | собранная статика — её отдаёт nginx |

### Кто что пишет в тома

| Том | Кто пишет | Что при деплое |
|---|---|---|
| `db_data` | Django, постоянно | **сохраняется** |
| `media_data` | Django при загрузке книг | **сохраняется** |
| `static_data` | `collectstatic` при старте контейнера | пересобирается целиком |

Только `static_data` перезаписывается — он спроектирован как пересоздаваемый
артефакт. Медиа и база переживают деплой.

### Почему статика едет в образ, а отдаётся из тома

`Dockerfile:41` кладёт исходники в `/app/static`, а `Dockerfile:49` создаёт
`/app/staticfiles` **пустым**. При старте контейнера `entrypoint.sh:14`
выполняет `collectstatic --clear`: каталог очищается и заполняется заново
строго под текущий образ.

Направление — от контейнера в том, а не наоборот. Статика не состояние, а
производный артефакт: пересборка образа пересобирает её заново.

Том при этом ценен тем, что **его же читает nginx** (`docker-compose.yml`,
`static_data:/app/staticfiles/:ro`). Если бы статика жила только в образе,
пришлось бы держать вторую копию для nginx.

### Осторожно: два разных вида монтирования

| Вид | Примеры в проекте | Поведение |
|---|---|---|
| **Именованный том** | `static_data`, `db_data`, `media_data` | Живёт внутри Docker, с хоста не прокидывается. Docker создаёт пустым и копирует из образа только при первом создании. Дальше пишет контейнер |
| **Bind mount** | `./nginx/nginx.conf`, `./backups` | Каталог хоста авторитетен с первой секунды и **перекрывает** образ |

Подложить старые файлы внутрь контейнера может только bind mount. В проекте
их два, и оба это предполагают.

`/app/media` в образе пустой: `Dockerfile:49` только создаёт каталог, ни одна
строка `COPY` туда ничего не кладёт, а `.dockerignore:15` исключает `media/`
из контекста сборки. `collectstatic --clear` очищает `STATIC_ROOT`
(`/app/staticfiles`) — это другой путь, `MEDIA_ROOT` он не затрагивает.

### Что может уничтожить содержимое томов

| Команда | Последствие |
|---|---|
| `docker compose down -v` | удаляет все тома: база и все медиафайлы |
| `docker compose up -V` | пересоздаёт тома, содержимое теряется |
| `docker volume rm media_data` | то же для одного тома |
| `docker system prune --volumes` | удаляет неиспользуемые тома |

В `make app-down` флага `-v` нет намеренно. `make prune-safe` вызывает только
`container prune`, `builder prune` и `image prune` — тома не трогает. Флаг `-V`
в проекте не используется нигде; если он встретился в команде, которую вы
запускаете, — отмените её.

## 2. Подготовка сервера (один раз)

Проект живёт в `/opt/book-club`. Git на сервере не используется: код приезжает
образом, а инфраструктурные файлы копируются вручную.

```bash
sudo mkdir -p /opt/book-club/nginx
cd /opt/book-club
cp .env.example .env
```

Заполнить в `.env`:

| Переменная | Значение |
|---|---|
| `DJANGO_SECRET_KEY` | `python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"` |
| `IMAGE` | `miran2025/book-club:0.0.1` |
| `DJANGO_ALLOWED_HOSTS` | хост приложения внутри сети |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | публичный адрес **без слеша в конце** |

Если репозиторий приватный — `docker login` на сервере.

### Ловушка: права на `backups`

`./backups` — bind mount, его нет в репозитории. Docker создаст каталог сам и
от **root**, а контейнер работает от uid 1000 и бэкапы писать не сможет.

```bash
mkdir -p /opt/book-club/backups
sudo chown 1000:1000 /opt/book-club/backups
```

## 3. Файлы инфраструктуры на сервере

На сервере лежат три файла. Они меняются редко и обновляются вручную — код
приезжает в образе, тянуть репозиторий ради них не нужно.

```bash
# с машины разработчика, когда эти файлы изменились
scp docker-compose.yml Makefile root@server:/opt/book-club/
scp nginx/nginx.conf root@server:/opt/book-club/nginx/
```

| Файл | Почему не может быть в образе |
|---|---|
| `docker-compose.yml` | им управляет Docker на хосте |
| `nginx/nginx.conf` | смонтирован с хоста |
| `Makefile` | ради `make deploy` с ожиданием healthcheck |

`.env` в этот список не входит: там секрет, он создаётся один раз вручную.

## 4. Первый деплой

На машине разработчика:

```bash
make test              # 218 тестов. Обязательно: в образе включён манифест статики
make check-migrations  # убедиться, что модель не разошлась с миграциями
make app-build
make app-push
```

На сервере — файлы инфраструктуры (раздел 3), затем:

```bash
make deploy
make verify
```

Ждать **30-60 секунд** — это не зависание: `--wait` ждёт healthcheck, а у
него `--start-period=20s --interval=30s`.

### Проверять нужно оба конца, а не только «контейнер healthy»

Первый запуск в бою показал, почему. Контейнер `web` был полностью здоров,
`/healthz/` отдавал 200 — а сайт не открывался, потому что **nginx не был
поднят вообще**: в `docker compose ps` была одна строка вместо двух.
Здоровье `web` ничего не говорит о доступности сайта.

Вторая ловушка: `200` на главной не означает, что работает статика.
Страница отрендерится, а картинки отдадут 404 — при этом сайт выглядит
«полуживым», и заметить трудно.

`make verify` проверяет три вещи последовательно и сразу показывает, где
обрыв:

| Проверка | Что доказывает |
|---|---|
| `docker compose ps` | подняты **оба** сервиса, `web` healthy |
| `healthz: 200` | приложение отвечает изнутри |
| `через nginx: 302` или `200` | nginx слушает и проксирует на web |
| `/static/...` → `200` | цепочка образ → `collectstatic` → том → nginx целостна |

Хост для проверок берётся из `DJANGO_ALLOWED_HOSTS` в `.env` — из того же
первого значения, что видит Django. Если он пуст, задайте переменную в
`.env`, иначе проверка получит `400` и запутает.

**Одноразовый переход.** В томе `static_data` лежат старые файлы без хешей.
Контейнер пересоберёт каталог при старте (`entrypoint.sh:14`). Пара секунд,
когда nginx отдаст 404 на `/static/`, ожидаемы.

## 5. Релизная процедура

Обычное изменение без миграций — две команды, одна на каждой машине:

```bash
# машина разработчика
make test && make app-build && make app-push

# сервер
make deploy
make verify
```

`make deploy` = `docker compose pull` + `up -d --wait`. Сервис намеренно не
указан: на первом запуске `up -d web` создал бы только web и оставил nginx
неподнятым.

На последующих деплоях лишнего простоя нет — compose пересоздаёт только то,
что действительно изменилось. Образ nginx запинен по digest, конфиг не
трогаем, значит работающий nginx остаётся нетронутым и `/static/` с
`/media/` не простаивают. Простой — несколько секунд, пока перезапускается
`web`.

Полный цикл с проверкой схемы БД — `make app-test-rebuild-push`
(тесты → проверка миграций → сборка → push).

Файлы инфраструктуры копируются на сервер только если менялись — при обычном
релизе приложения этого делать не нужно.

## 6. Если меняется модель БД

Миграция создаётся **на машине разработчика** и едет в образ вместе с кодом.

```bash
make makemigrations   # создаёт файл в src/*/migrations/
make migrate-local    # применить к локальной базе
git add src/*/migrations/    # без этого файл не попадёт в образ
make test && make app-build && make app-push
```

На сервере дополнительных шагов нет: `entrypoint.sh:11` применяет миграции
при старте контейнера, до gunicorn. Вручную `manage.py migrate` на сервере
запускать не нужно.

### Миграции обязаны быть обратно совместимы

Откат кода мгновенный, а окна, где старая и новая версия работают
одновременно, не существует. Несовместимая миграция уронит прод при откате.

1. **expand** — добавить новое, не трогая старое: nullable-колонки, новая
   таблица. Старый код продолжает работать.
2. **contract** — применять только после того, как новая версия отработала
   на проде весь необходимый срок.

## 7. Откат

Тег образа плавающий (`:0.0.1`), поэтому откат держится на том, что предыдущий
образ сохранился локально. Именно поэтому `make prune-safe` не использует
`-a/--all`.

```bash
make rollback
```

Команда печатает шаги с актуальными именами. Суть: возвращаем тег
предыдущему локальному образу, затем `make deploy`.

```bash
docker images miran2025/book-club --format 'table {{.ID}}\t{{.CreatedAt}}\t{{.Tag}}'
docker tag <IMAGE_ID> miran2025/book-club:0.0.1
make deploy
make verify
```

Если к откатываемой версии относились миграции, база откатывается из бэкапа:

1. остановить приложение (`make app-down`)
2. вернуть файл бэкапа в том `db_data` — вместе с `-wal` и `-shm`, либо
   предварительно сделав checkpoint
3. `make deploy`

Порядок обязателен: при работающем процессе SQLite держит файл открытым.

## 8. Регулярные операции

### Бэкап

`make backup` — снимок через backup API модуля `sqlite3`
(`sqlite3.Connection.backup()`), не `cp`: при активном WAL копирование файла
может поймать незакоммиченные страницы. Хранятся 7 последних копий в
`/opt/book-club/backups`.

Раз в сутки, crontab на сервере:

```cron
17 4 * * * cd /opt/book-club && make backup >> /var/log/bookclub-backup.log 2>&1
```

Полный бэкап сервера делает системный администратор.

### Чистка мусора

```bash
make prune-safe
```

Раз в пару недель вручную. Без `-a`, предыдущий образ не пострадает. Тома не
трогаются: в них база, медиа и собранная статика.

### Логи

```bash
docker compose logs -f web | tail -50
docker compose logs -f nginx
```

Ротация настроена в `docker-compose.yml`: `json-file`, `10m` × `5` файлов.

## 9. Ограничения SQLite

Решение владельца: SQLite остаётся навсегда. Ниже — не риски, а свойства
системы, которые нужно знать.

- **Один писатель.** Второй контейнер приложения против той же базы даёт
  `database is locked`. Blue/green и горизонтальное масштабирование
  невозможны — это свойство системы, а не ограничение по желанию. Краткий
  простой `web` при деплое неизбежен.
- **Конкуренция.** `--workers 2 --threads 2` — до четырёх параллельных
  запросов к базе. При одновременной записи часть выждет `timeout: 20` и
  получит 500. На странице голосования одновременно ходят несколько
  участников. Это предел системы, его нужно знать, а не обходить.
- **`synchronous=NORMAL`** в WAL: аварийное выключение питания ОС может
  потерять недавние транзакции, не повредив саму базу. Для голосования с
  дедлайном 31.12.2026 потеря голосов ощутима. Значение оставлено осознанно;
  переход на `FULL` — вопрос наличия UPS на сервере.
- **`docker compose down -v` удаляет тома**, а вместе с ними базу и медиа,
  молча и безвозвратно. В `make app-down` флага `-v` намеренно нет. Полный
  список опасных команд — в разделе 1.
- Настроено и менять не нужно: `journal_mode=WAL`, `timeout: 20`
  (`src/config/settings.py`).

## 10. Статика

Собирается **только внутри контейнера** (`collectstatic` в
`docker/entrypoint.sh`). Перенос папки `staticfiles` с рабочей машины на
сервер не допускается: это смесь файлов проекта и ассетов Django из
локального `.venv`, а в образе админские ассеты из другой версии.

Включён `ManifestStaticFilesStorage`: имена содержат хеш
(`hero-miran.b06473d632b6.jpg`), поэтому `expires 30d` в `nginx/nginx.conf`
перестаёт годами отдавать устаревшие версии.

### Сборка не проверяет ссылки `{% static %}`

Ссылка на несуществующий файл **проходит `collectstatic` молча**, а падает
уже при рендере — `ValueError: Missing staticfiles manifest entry`, то есть
500 на странице.

Единственная защита — тесты: `conftest.py` собирает статику перед прогоном,
поэтому такая ошибка валит тест, а не прод. **Тесты запускаются до сборки
образа** (`make test`).

## 11. Шпаргалка

```bash
# машина разработчика
make test                          # тесты
make check-migrations              # модель vs миграции
make makemigrations                # создать миграцию
make migrate-local                 # применить локально
make app-build                     # собрать образ
make app-push                      # отправить в registry

# сервер
make deploy                        # обновить и дождаться healthy
make verify                        # контейнеры, nginx, статика — три точки
make backup                        # снимок базы
make rollback                      # инструкция по откату
make prune-safe                    # чистка мусора
make app-down                      # остановить (без -v!)
docker compose ps
docker compose logs -f web
```
